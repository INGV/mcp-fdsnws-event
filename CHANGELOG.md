# Release Notes

### Release 2.0.0-dev (2026-09-22)
  - fix: bound the size of every tool result, so that a single answer can no longer push the user's own question out of the model's context window. On Ollama 0.34.0 with `qwen3.8:27b` at a 32k context, asking for a table of arrivals returned a tool payload of 278800 bytes, many times the window on its own; the runtime drops messages from the front of the prompt until it fits, which left only that payload, and the qwen3.5 renderer then refused a prompt containing no user turn with `no user query found in messages`. The failure named neither the tool nor the size, and raising the context length did not fix it: the server has to bound its own output. The same question, on the same event (INGV `47219912`), now sends 31680 bytes for a first page of 90 arrival rows and gets HTTP 200 at 16907 prompt tokens, 52% of the window
  - feat: return station-level collections as a table (`columns` + `rows`) instead of a list of QuakeML objects. A table states each field name once instead of once per row, and the repeated `smi:` identifier boilerplate is lifted into an envelope-level `id_prefixes` map with only the remainder left in the rows, so prefix plus row value still reconstructs the identifier character for character. Measured on an INGV Mw 6.1 event, the arrivals of `fdsn_get_arrivals_by_eventid` go from 805 kB to 87 kB at the same information content. Breaking: callers that walked an `arrivals` array must be rewritten against the table
  - feat: drop the picks, amplitudes and station magnitudes that `fdsn_get_earthquake_by_eventid` used to inline. That response was the largest this server could produce — 3510 kB on the same INGV Mw 6.1 event, of which 1886 kB was amplitudes alone — and it shipped thousands of station readings to answer "what was this earthquake". It is now 6 kB: event metadata, preferred origin, preferred magnitude and focal mechanisms, plus `station_magnitudes_count` and `amplitudes_count` so a caller knows whether the dedicated tools have anything to return. Breaking for anyone reading those collections from this tool
  - feat: rename every event-keyed tool from `_by_id` to `_by_eventid` (`fdsn_get_earthquake_by_eventid`, `fdsn_get_arrivals_by_eventid`, `fdsn_get_allorigins_by_eventid`, `fdsn_get_allmagnitudes_by_eventid`, `fdsn_get_focalmechanism_by_eventid`). The suffix now names the input the caller must supply rather than the QuakeML class the data comes from: arrivals and station magnitudes belong to an Origin, but no FDSN node accepts an origin id, so a tool called `_by_originid` would still take an event id and would invite a model to invent one. Breaking: every mcpo and Open WebUI registration must be re-imported, since the callable names change (in Open WebUI they become `tool_fdsn_get_arrivals_by_eventid_post` and so on)
  - feat: add `fdsn_get_stationmagnitudes_by_eventid` and `fdsn_get_amplitudes_by_eventid`, which return the per-station magnitude readings and the measured amplitudes as tables. These were previously reachable only by downloading the whole event, and they are the data behind the question "which stations contributed to this magnitude". Both send `includearrivals`, without which EMSC publishes neither, and fall back to a plain fetch when the datacenter answers HTTP 501 to that flag, as USGS does
  - feat: return arrival and station-magnitude rows for every origin the datacenter delivered, marking the preferred solution with `is_preferred_origin` and identifying the others with `origin_id`. Restricting to the preferred origin would have been invisible data loss on EMSC, where one event spreads its arrivals over six origins (137 preferred, 137 elsewhere); on INGV everything already sits on the preferred origin, so the rule costs nothing there
  - feat: paginate every table with `limit` and `offset`, answering with `returned_count`, `has_more` and `next_offset`, and filter rows by `network` and `station` (plus `magnitude_type` on station magnitudes). The filters are applied by this server after the fetch, because no FDSN event service filters a sub-resource by station, so that "the amplitude at station SGRT" costs one small answer instead of a walk through every reading of the event
  - feat: normalize the column names of `fdsn_query_earthquakes` onto the fourteen names of the FDSN 1.2 text profile, and move `returned_count`, `limit`, `offset`, `has_more` and `next_offset` to the top level of the response. The datacenters spell their own header differently — INGV writes `Depth/Km`, EMSC, GFZ and USGS write `Depth/km`, and `EventType` is absent from EMSC and USGS — so a client could not be written against a column name without knowing who had answered. Breaking: `depth_km`, `event_id`, `location_name` and the rest replace the passthrough header, and the `pagination` object is gone
  - feat: make every limit an environment variable read at import (`FDSN_MAX_RESULT_BYTES`, `FDSN_MAX_ROWS_*`, `FDSN_DEFAULT_ROWS_*`), documented in the README and in a committed `.env.example`. They are read at import rather than per request because each maximum is published as the `maximum` of that tool's `limit` parameter in the JSON schema advertised in `tools/list`: changing one changes what the model is told it may ask for, so a restart, and a refresh of any cached tool schema, is required. A bad value degrades to the default with a warning, and a default above its own maximum is clamped rather than failing the server at import
  - fix: calibrate the byte budget against a measured token density instead of an assumed one. The first cut of this release assumed 2.4 bytes per token, which made a 60000 byte budget look like 25k tokens and therefore comfortable. Differencing `prompt_eval_count` across payload sizes on the deployed model gives 1.87 bytes per token, linear (1511 bytes cost 476 tokens, 48667 cost 25744), at which the same budget is 32150 tokens — 98% of a 32k context window, a milder form of the very failure this release exists to fix. `FDSN_MAX_RESULT_BYTES` is therefore 36000, about 19250 tokens or 59% of the window, and each table's maximum is that budget divided by the widest row the finished tool actually emitted against INGV, EMSC, GFZ and USGS: arrivals 90, station magnitudes 220, amplitudes 125, events 240. These figures are policy calibrated for a 32k window, not a property of the data: a deployment with a larger window is exactly what the variables are there to be raised for
  - fix: advertise the row limits in the tool schema. FastMCP builds the published JSON schema from the tool function's signature rather than from the Pydantic model validated inside it, so a bare `limit: int` carried no maximum at all: a model asking for `limit: 1000` was told nothing beforehand and got an unexplained validation error afterwards. The `limit` parameters are now annotated at the signature, so `tools/list` carries their minimum, maximum and default
  - docs: document the table response shape, the identifier prefixes, pagination and the filters in the README, add a configuration section covering the three ways the variables reach the container (`docker run -e`, the `args` of an MCP client entry, and a compose `environment:` block), and add a breaking-changes section for the upgrade from 1.x

### Release 1.6.0 (2026-07-30)
  - fix: report a provider that does not implement a requested `include*` flag through the structured error contract instead of crashing. ObsPy rejects such a flag from the provider's own service description by raising a bare `TypeError` before any request is issued, which escaped the by-id tools unhandled; EMSC does not implement `includeallmagnitudes` and USGS does not implement `includearrivals`, so `fdsn_get_allmagnitudes_by_id`, `fdsn_get_focalmechanism_by_id` and `fdsn_get_arrivals_by_id` were affected. The conversion is restricted to the flags this server actually sends, so a wrong keyword argument on our side still surfaces as a bug
  - test: drive the by-id contracts from QuakeML documents captured per provider and per `include*` flag set, parsed through the production ObsPy path, so the whole tool-by-provider matrix stays reproducible while the services are unreachable. Seventeen of the twenty cells run from captured QuakeML; the three the providers do not implement are pinned by their captured error bodies. The INGV event is `45376822`, chosen because it is complete down to a focal mechanism with a moment tensor, so every INGV cell serializes real content. Offline suite grows from 72 to 96 tests
